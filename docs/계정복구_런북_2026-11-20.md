# 계정 복구 런북 — 가비아 이전 후 로그인 불가

## 0. 증상과 원인

**증상**: 가비아 이전 후 기존 아이디로 로그인이 안 된다.

**원인 후보 3개 (실측으로 확인)**

| # | 원인 | 확인 방법 |
|---|---|---|
| 1 | **게이트웨이에 비밀키가 설정돼 있는데 앱은 키를 모른다** | `SYNC_SECRET` 설정 여부 |
| 2 | **서버 데이터에 계정 행이 없다** | `--list` 로 레지스트리 확인 |
| 3 | 마스터 아이디(`june7486`)는 새로 만들 수 없다 | 아래 4-3 |

### 원인 1이 가장 유력합니다

코드 확인 결과:

```
게이트웨이에 SYNC_SECRET 이 있으면  →  키 없는 요청은 전부 401
앱은 키를 보낼 수단이 없다          →  401 이 계속된다
```

앱에 키를 넣는 경로는 `settings_screen.dart` 의 `_NasPanel` **하나뿐**입니다.
그리고 `_NasPanel` 은 **로그인한 뒤에만** 들어갈 수 있는 설정 화면 안에 있습니다.

**즉 닭과 달걀입니다.** 서버 인증을 풀려면 설정에 들어가야 하는데,
설정에 들어가려면 로그인을 해야 합니다.

> 이전 턴에 제가 "같은 출처라 설정이 필요 없다"고 말씀드렸는데, 그건 **앱이 자동으로 `/api/` 를
> 찾는다**는 뜻이었습니다. **게이트웨이가 키를 요구하면 이야기가 달라집니다.** 정정합니다.

**해결**: 서버 쪽에서 `SYNC_SECRET` 을 비웁니다. 그러면 루프백(127.0.0.1) 전용으로 열립니다.

## 1. 진단 — 3분

```bash
# (가) 게이트웨이에 키가 설정돼 있나?  ★여기가 핵심
sudo grep -n '^SYNC_SECRET=' /srv/june7486/sites/scheduler/.env
#   값이 보이면 → 원인 1.  값이 비어있으면 → 원인 2로.

# (나) 서버가 401 을 뱉나?
curl -s -o /dev/null -w 'health: %{http_code}\n' http://127.0.0.1:8097/health
curl -s -o /dev/null -w 'state : %{http_code}\n' \
  "http://127.0.0.1:8097/api/state?ws=ACCREGISTRYJUNESCHEDULER0001"
#   401 이면 → 원인 1 확정

# (다) 계정 명부 확인
sudo python3 recover_accounts.py /srv/june7486/sites/scheduler/data --list
#   "계정 0개" 또는 "레지스트리 없음" → 원인 2
```

## 2. 처방 — 원인별

### 2-1. 원인 1 (키가 원인) — 권장

```bash
cd /srv/june7486/sites/scheduler
sudo cp -a .env .env.bak.$(date +%Y%m%d-%H%M%S)

# SYNC_SECRET 을 빈 값으로 (앞에 # 을 붙여 주석 처리해도 됩니다)
sudo sed -i 's|^SYNC_SECRET=.*|SYNC_SECRET=|' .env
sudo grep -n '^SYNC_SECRET=' .env    # 빈 값 확인

sudo systemctl restart june-gateway
sleep 2
curl -s -o /dev/null -w 'readyz: %{http_code}\n'  http://127.0.0.1:8097/readyz
curl -s -o /dev/null -w 'state : %{http_code}\n' \
  "http://127.0.0.1:8097/api/state?ws=ACCREGISTRYJUNESCHEDULER0001"
#   readyz 200, state 200 이면 성공
```

**왜 안전한가**: `HOST=127.0.0.1` 이므로 외부에서 8097 로 직접 못 들어옵니다.
Nginx 를 거쳐야만 닿습니다. 키가 없어도 루프백 밖으로 새지 않습니다.

### 2-2. 원인 2 (계정 행이 없음) — 비밀번호 다시 심기

로그인은 되는데 비밀번호가 안 맞는 경우, 또는 레지스트리가 비어있는 경우입니다.

```bash
# 미리보기 (파일을 쓰지 않음)
sudo python3 recover_accounts.py /srv/june7486/sites/scheduler/data \
     --reset-pw 아이디 --pw '새비밀번호'

# 실제 적용
sudo python3 recover_accounts.py /srv/june7486/sites/scheduler/data \
     --reset-pw 아이디 --pw '새비밀번호' --apply
```

**이 도구가 하는 일**
- 실행 전 `data/.backup-accounts-<시각>/` 에 **전체 백업** 생성
- 레지스트리와 그 계정의 워크스페이스 **양쪽**에 계정 행을 심음
- **일정(`tasks/`)·카테고리·로그는 건드리지 않음**
- 기존 표시이름·생성일은 보존
- 게이트웨이 캐시(`/api/drop`)를 비움
- 비밀번호는 **해시만** 기록. 평문은 남기지 않음

### 2-3. 마스터 아이디 `june7486` 를 새로 만들어야 할 때

`june7486` 은 앱이 부팅할 때 `_ensureMaster()` 로 로컬에 자동 생성합니다.
그래서 `addUser('june7486', ...)` 은 **"That ID already exists."** 로 거부됩니다.
앱 화면에서는 만들 수 없습니다. 반드시 서버 쪽에서 심어야 합니다.

```bash
sudo python3 recover_accounts.py /srv/june7486/sites/scheduler/data \
     --create june7486 --pw '새비밀번호' --name '이승준' --master --apply
```

## 3. 환경변수 방식 — 재발 방지 (권장)

지금은 서버 주소가 기기 로컬(Hive)에만 있어서, 새 기기마다 다시 넣어야 합니다.
빌드에 주소를 박으면 이 과정이 사라집니다.

```
--dart-define=SYNC_URL=https://sch.june7486.com
                                   ↑ /api 를 붙이지 마십시오
```

**실측**: `/api` 를 붙이면 **로그인이 실패합니다.** 앱이 `/api/state` 를 스스로 붙이기 때문에
`.../api/api/state` 가 되어 404 가 납니다. **출처(origin)만** 넣으십시오.

| SYNC_URL | 결과 |
|---|---|
| `http://127.0.0.1:8099` (출처만) | **성공** |
| `http://127.0.0.1:8099/api` | **실패** |

**주의**: `SYNC_KEY` 는 **절대 빌드에 넣지 마십시오.** 2026-11-20 에 그렇게 했다가
`main.dart.js` 에 키가 평문으로 박혀 노출됐습니다. 키는 서버에서 비우는 쪽이 맞습니다.

## 4. 복구 검증 (실측 결과)

실제 게이트웨이 + 실제 `Store` 로 확인한 결과입니다.

| 검증 | 결과 |
|---|---|
| 기기A 계정 생성 → 기기B(신규) 로그인 | **성공** |
| 기기A 일정 → 기기B 동기화 후 도착 | **성공** (1개 도착) |
| 옛 비밀번호 거부 | **성공** (거부됨) |
| 도구로 재설정한 새 비번으로 로그인 | **성공** |
| 재설정 후 표시이름 | **보존됨** |
| 재설정 후 기존 일정 | **보존됨** |
| 재설정 후 잘못된 비번 거부 | **정상** |
| 서버 주소가 앱 재시작 후에도 유지 | **유지됨** |

**부수 확인**: `june7486` 은 신규 기기에서 앱 화면으로 계정 생성이 **불가능**합니다
(`_ensureMaster` 선점 때문). 서버 주입이 유일한 길입니다.

## 6. 되돌리기

```bash
# 계정 재설정 되돌리기 — 가장 최근 백업에서 복원
LATEST=$(ls -dt /srv/june7486/sites/scheduler/data/.backup-accounts-* | head -1)
echo "복원 원본: $LATEST"
sudo cp -a "$LATEST"/*.json /srv/june7486/sites/scheduler/data/
sudo systemctl restart june-gateway

# .env 되돌리기
LATEST_ENV=$(ls -t /srv/june7486/sites/scheduler/.env.bak.* | head -1)
sudo cp -a "$LATEST_ENV" /srv/june7486/sites/scheduler/.env
sudo systemctl restart june-gateway
```
