## 2. 서버가 필요한가 — 대부분 불필요

### 정적 웹앱으로 충분한 이유

사용자 일정은 **브라우저 안(IndexedDB)** 에 저장됩니다.

| 질문 | 답 |
|---|---|
| 서버 DB 가 있나 | **없음** |
| 외부 API 호출이 있나 | **없음** |
| 인증 서버가 있나 | **없음** (계정은 브라우저 저장소 기준) |
| OAuth 토큰을 쓰나 | **없음** |
| 서버 없이 배포 가능한가 | **가능** |

### 서버가 필요한 유일한 경우 — 동기화(선택)

여러 기기에서 같은 자료를 볼 때만 필요합니다. **없어도 앱은 동작합니다.**

| 항목 | 값 | 근거 (파일:행) |
|---|---|---|
| 수신 포트 | **8097** | `server/gateway/server.js:49` |
| 바인딩 주소 | **127.0.0.1** | `server/gateway/server.js:72` |

```js
// server/gateway/server.js
const PORT = Number(process.env.PORT || 8097);        // 49행
const HOST = (process.env.HOST || '127.0.0.1').trim(); // 72행
```

> **4103 은 쓰지 않습니다.** 회신 2페이지에서 "4103 은 최초 제안일 뿐 필수
> 계약이 아니다"라고 하셨고, 실제 코드도 8097 입니다. **8097 을 기준으로
> 잡아주세요.** (예전 문서 숫자를 운영값으로 가정하지 않았습니다.)

> ⚠️ **8097 을 인터넷에 직접 열지 마세요.** 앞단 Nginx 가 `/api/` 를 받아
> 넘기는 구조입니다. 직접 노출하면 인증이 공유키 하나뿐이라 위험합니다.
> `PORT=8097 node server.js` 만으로는 루프백이 보장되지 않으니, 회신 2페이지
> 지적대로 **바인딩을 별도로 확인**해 주세요. (`ss -ltnp | grep 8097`)

## 3. 일정 데이터 처리 — 이전 시 주의

### 저장 위치

브라우저 **IndexedDB**. 출처(origin) 단위로 격리됩니다.

### ⚠️ 주소를 바꾸면 데이터가 따라오지 않습니다

`www.aqdesign.co.kr` 에서 쓰던 일정은 새 주소에서 **보이지 않습니다.**
앱에 내보내기/가져오기가 있으므로 개발은 불필요하고 **사용자 안내문**만
필요합니다.

```
옛 주소에서: 설정 → 백업 → JSON 다운로드
새 주소에서: 설정 → 백업 복원 → JSON 선택
```

> ⚠️ **복구는 덮어쓰기입니다. 병합이 아닙니다.**
> 복구 전에 현재 데이터를 먼저 백업하라고 안내문에 반드시 넣어야 합니다.

### 시간대

`dueDate` 는 ISO-8601 문자열이며 **시간대 정보가 없습니다**
(`2026-11-20T09:00:00`). 그 기기의 벽시계 시각으로 저장·표시됩니다.
`updatedAt` / `deletedAt` 은 epoch 밀리초입니다.

→ 가상 일정으로 검사했습니다: 왕복 보존, 반복 4종, 자정·연말·윤일 경계
무밀림. **실제 일정·캘린더 계정은 쓰지 않았습니다.**

### 외부 캘린더 연동

**딥링크만** 있습니다. Google Calendar 에 일정을 *열어주는* 링크를 띄울 뿐,
OAuth 도 콜백 URL 도 없습니다.

→ **주소를 바꿔도 바꿀 콜백 주소가 없습니다.** 별도 설정 불필요.

## 4. 웹 서빙 조건 — 세 가지만 지켜주세요

| # | 조건 | 틀리면 |
|---|---|---|
| 1 | `.wasm` → `application/wasm` | CanvasKit 로드 실패 → **흰 화면** |
| 2 | `index.html` 캐시 금지 | 사용자가 영원히 옛 버전을 봄 |
| 3 | `version.json` 캐시 금지 | 업데이트 확인이 조용히 거짓말을 함 |

**확인 명령**

```bash
curl -sSI https://<도메인>/canvaskit/canvaskit.wasm | grep -i content-type
# → content-type: application/wasm

curl -sSI https://<도메인>/version.json | grep -i cache-control
# → no-cache
```

> 회신 7페이지 지적 반영: **`.htaccess` 는 Apache 전용**이라 Nginx 는
> 무시합니다. MIME 은 `mime.types` 또는 `location` 블록에서 잡아야 합니다.
> 회신 4~5페이지에서 "기존 scheduler 용 Nginx 예시가 `/` 전체를 4103 으로
> 프록시하니 그대로 적용하면 안 된다"고 하신 점도 반영해, **정적 서빙과
> `/api/` 만 프록시**하는 설정을 별도로 준비했습니다
> (`server/gateway/nginx-scheduler-gabia.conf`).

## 5. 수신기 규격 — **제안** (합의 필요)

> ⚠️ 확정안이 아닙니다. 이와 다르게 구현되시면 제 도구를 그 규격에 맞춰
> 고치겠습니다. 아래는 "이렇게 하면 안전하다"는 제안입니다.

### 5-1. 엔드포인트

```
POST https://<호스트>/scheduler/upload
```

- **scheduler 전용 경로**를 씁니다. 다른 앱과 섞이지 않게.
- **웹에서 접근할 수 없어야 합니다.** 공개 정적 경로(`/` 아래)에 두지 말고,
  서버 측 인증을 요구하는 경로로 두세요. 브라우저로 열면 401 이어야 정상.

### 5-2. 인증 — 헤더 두 개

```
X-Submit-Id:    <제출자 식별자>
X-Submit-Token: <업로드 토큰>
```

- **쿼리스트링에 넣지 마세요.** 프록시·access log 에 그대로 남습니다.
- 본문에도 넣지 마세요. multipart 파서가 실패 로그에 본문 일부를 남깁니다.
- 서버는 토큰을 **해시로 저장**하고 **타이밍 안전 비교**를 쓰세요.
- 최소 **32바이트 무작위** 값 권장.

### 5-3. 요청 본문 — `multipart/form-data`

| 필드 | 형식 | 설명 |
|---|---|---|
| `app_id` | text | 항상 `scheduler` |
| `release_id` | text | `rel-YYYYMMDD-HHMMSS-<sha7>` |
| `commit_sha` | text | 전체 40자 소스 커밋 |
| `zip_sha256` | text | 클라이언트가 계산한 ZIP 해시 |
| `manifest_sha256` | text | 매니페스트 JSON 의 해시 |
| `package` | file | `application/zip` |

### 5-4. 응답 — 200 또는 201

```json
{
  "ok": true,
  "receipt_id": "rcpt-20261120-0001",
  "release_id": "rel-20261120-123110-4c291f7",
  "zip_sha256": "<서버가 실제 수신 바이트로 계산한 해시>",
  "received_at": "2026-11-20T12:31:10Z"
}
```

### ⚠️ 5-5. 가장 중요한 항목

> **`zip_sha256` 은 서버가 받은 바이트로 직접 계산해야 합니다.**
> 클라이언트가 보낸 값을 그대로 되돌려주면 **검증이 아닙니다.**
> 그래야 전송 중 손상·절단을 잡을 수 있습니다.
> **이것이 "접수 확인"의 유일한 근거입니다.**

저는 **서버 접수 ID 와 서버가 계산한 해시가 둘 다 일치할 때만** "수신 완료"로
보고합니다. 둘 중 하나라도 없으면 "확인 불가"로 보고합니다. 이 원칙은
양보하지 않습니다 — 확인하지 않은 것을 확인했다고 말하지 않겠습니다.

### 5-6. 오류 응답

| 상태 | 의미 | 제 동작 |
|---|---|---|
| 400 | 형식 오류 | 재시도 무의미 — 보고 |
| 401 / 403 | 인증 실패 | 재시도 무의미 — 보고 |
| 409 | 같은 릴리스 ID 존재 | **덮어쓰지 않음** — 새 ID 로 재시도 |
| 413 | 너무 큼 | 보고 |
| 5xx | 서버 오류 | 담당자에게 보고 |

### 5-7. 중복 방지

- 릴리스 ID 는 `rel-<시각>-<커밋7>` 형식이며 제출마다 새로 만들어집니다.
- 같은 `release_id` 는 **덮어쓰지 말고 409** 로 거절해 주세요.
- 같은 `zip_sha256` 이 이미 있으면 409 로 거절해도 됩니다(진짜 중복).

### 5-8. 받은 뒤 서버가 할 일

1. ZIP 을 받아 `zip_sha256` **직접 계산**하고 응답에 담기
2. 압축을 풀어 `manifest.json` 의 파일별 해시 검증
3. 통과한 것만 배포 후보로 승격
4. 반영은 **수동 승인** 후에 (자동 배포 금지)

## 7. 🔴 먼저 알려드려야 할 것 — 키 노출 사고와 조치

이번 작업 중 발견한 사실입니다. **수신기 설계에 직접 영향**이 있어 먼저
알립니다.

### 무슨 일이 있었나

이전 배포 스크립트가 `--dart-define` 으로 **동기화 키와 NAS 주소를 웹 번들에
심었고**, 그 번들이 공개 서빙됐습니다. 외부 IP 가 그 주소의 DSM 로그인
화면까지 도달한 기록이 있습니다.

### 우리가 한 조치

- 빌드에서 해당 define 제거 (공개 배포본에 주소·키를 심지 않음)
- 배포 스크립트에 **누출 검사 게이트**를 넣어, 발견 시 배포를 중단
- 제출 패키지 생성 시 **파일 내용까지** 검사 (이름만 보던 방식 보완)
- 사고 문서에 인용돼 있던 **키 원문·호스트명을 소스에서 전량 삭제**
- 키 회전 절차 문서화 (`server/gateway/KEY-ROTATION.md`)

### 수신기 설계에 주는 시사점

1. **키를 정적 번들에 심는 구조를 만들지 마세요.** 브라우저가 결국 알아야
   하는 값은 비밀이 될 수 없습니다.
2. 수신 인증은 **번들에 없는 값**(제출 토큰)이어야 합니다.
3. 수신 경로를 **공개 정적 경로 아래에 두면 안 됩니다.**

## 9. 승인·확인 부탁드릴 것

회신 4~5페이지 질문에 대한 제 답과, 새로 확인이 필요한 항목입니다.

| # | 항목 | 제 입장 / 요청 |
|---|---|---|
| 1 | **포트** | **8097** 확정 희망 (4103 은 폐기). 충돌 여부 확인 부탁 |
| 2 | **바인딩** | `127.0.0.1` 이며 인터넷 직접 노출 금지. 확인 방법 공유 부탁 |

| 6 | **Nginx 예시** | 기존 "`/` 전체를 4103 프록시" 예시는 **폐기**하고 정적+`/api/` 만으로 교체 |
| 7 | **수신기 규격** | 5장 제안 검토. 다르게 하실 부분 알려주시면 도구를 맞추겠습니다 |
| 8 | **`files.june7486.com`** | 아직 미정이라고 하셨는데, 수신기 호스트를 어디로 할지 |
| 9 | **serving 조건** | `.wasm` MIME·캐시 정책 3종 적용 가능한지 |
| 10 | **키 회전 일정** | `KEY-ROTATION.md` 절차대로 진행할 시점 조율 |

### 아직 준비되지 않은 것 (제 쪽)

- **수신 URL·Submit ID·Submit Token** — 받지 못했습니다. 이것이 없으면
  전송·접수 확인이 불가능합니다. **실행 환경변수로만** 주세요.
  (채팅·코드·ZIP·로그에 남기지 않겠습니다.)
- **빌드 최신화** — 업데이트 확인 기능이 최신 빌드에 아직 반영되지
  않았습니다. 제출 전에 처리할 예정입니다.
