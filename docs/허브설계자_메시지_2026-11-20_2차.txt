1. 실측으로 닫은 것 — 동일 출처에서 정말 동작하는가
================================================================================

지난 보고에서는 "게이트웨이는 뜨지만 정적 번들과 같은 출처에서 실제로
도는지는 미확인"이라고 적었습니다. 이번에 그 부분을 닫았습니다. 방법은
가비아 구성을 흉내낸 중간 서버를 세우고, 배포 예정 번들을 그 위에 올린 뒤,
브라우저에서 앱 화면을 실제로 띄워 확인하는 것입니다. 정적 파일과 /api/
프록시를 한 출처에 두는 구조는 가비아 Nginx 와 동일하게 맞췄습니다.

  확인 ①  앱 화면이 뜨는가
           로그인 화면 정상 표시. 하단 버전 표기까지 확인
  확인 ②  같은 출처 /health
           200 · 게이트웨이가 응답 (정적 파일 아님)
  확인 ③  같은 출처 /api/state
           200 · 문서 존재 · rev 2 · 엔티티 2건
  확인 ④  같은 출처 /api/push
           200 · rev 2 → 3 · 엔티티 3건

즉 "정적 서빙 + 접두사 보존 프록시"가 한 출처에서 성립하고, 앱이 그 통로로
실제 데이터를 읽고 씁니다. 지난 보고에서 미확인이던 부분은 이것으로 닫힙니다.

다만 이 시험은 제 샌드박스 안입니다. 가비아 실환경 확인을 대신하지 않습니다.

2. 접두사 규칙 — 문서 제안에서 실측 확인으로
================================================================================

지난 보고에서 접두사 유지(끝 슬래시 없음)를 제안드렸고, TO_BE_CONFIRMED
항목이라 확정을 요청드린 상태입니다. 이번 시험에서 그 값으로 실제 동작하는
것을 확인했습니다.

  사용한 형태   proxy_pass http://127.0.0.1:8097;      (끝에 슬래시 없음)
  결과          /api/state, /api/push 모두 정상 응답

슬래시를 붙이면 접두사가 잘려 404 가 되는 것도 함께 확인했습니다. 증상이
"게이트웨이는 살아 있는데 앱만 동기화 실패"로 나타나 원인 추적이 어렵습니다.
이 항목은 이제 허브 명세에서 확정해 주셔도 되는 상태입니다. 함께 /health 와
/readyz 가 /api/ 밖의 루트 경로라 별도 전달이 필요하다는 점도 그대로입니다.
지난 보고 6-5 에 적은 두 줄을 명세에 넣어 주시면 맞춰 두겠습니다.

3. 저장 구조 확정 — 쓰기 지점은 한 곳뿐입니다
================================================================================

지난 보고 4-4 에서 "이전 시 네 가지를 정해야 한다"고 적었습니다. 이번에
전부 정했습니다. NAS 를 저장소에서 제외하는 방향으로 확정했습니다.

  원본 기준 저장소   가비아 서버 디스크 한 곳. NAS 는 저장소가 아님
  쓰기 지점          하나. 이중 쓰기 없음. 두 곳에 쓰지 않음
  데이터 위치        /srv/june7486/sites/scheduler/data
  위치 제약          정적 공개 폴더와 버전별 배포 폴더 밖
  파일 단위          워크스페이스 1개당 JSON 1개
  파일 이름          <워크스페이스키>.json
  파일 내용          rev / gen / entities 세 키
  쓰기 방식          임시 파일에 쓴 뒤 교체. 반쪽 파일 없음
  재시작·업데이트    덮어쓰지 않음. 배포 폴더와 분리되어 불변

NAS 를 뺀 이유는 두 가지입니다. 첫째, NAS 가 꺼지면 앱 전체가 멈춥니다.
둘째, NAS 를 인터넷에 노출해야 하고 그것이 2026-11-20 사건의 경로였습니다.
이 결정으로 회신에서 지적하신 "이중 쓰기 금지" 조건이 구조적으로 만족됩니다.
두 곳에 쓸 방법 자체가 없습니다.

4. 발견한 결함 — 제 쪽 문제입니다
================================================================================

[결함 1] 보안 헤더가 일부 응답에서 빠집니다 — 심각도 중, 고칠 예정

제가 작성한 Nginx 설정에서, location 블록 안에 헤더 지시자를 쓰면 상위
서버 블록의 헤더가 상속되지 않고 대체됩니다. 상위에 세 개를 걸어두었는데,
그 안에서 다른 헤더를 지정한 블록에서는 세 개가 사라집니다.

  현재 상태   서버 블록에 3종을 걸어둠
              nosniff / Referrer-Policy / X-Frame-Options
              그런데 /health, /readyz, /api/, .wasm, 진입점에서 누락
  영향        기능 장애 아님. 정상 동작합니다
              다만 그 응답에 보안 헤더가 실리지 않습니다
  수정 방향   세 줄을 각 블록에 복사하거나 공통 조각으로 분리

운영 설치 전에 고치는 편이 맞습니다. 지금은 보고만 합니다. 재빌드가
필요한 문제가 아니라 설정 파일 문제입니다.

[결함 2] /health 응답의 필드 이름이 실제와 어긋납니다 — 심각도 낮, 판단 요청

지난 보고 6-3 에서 /health 의 의미를 정의해 드렸습니다. 그 정의는 그대로
유효한데, 응답에 실리는 이름 두 개가 NAS 시절 그대로입니다.

  service   "june-nas-gateway"   게이트웨이 식별자
  nas       true                 로컬 저장 모드에서는
                                 "데이터 폴더에 쓸 수 있는가"를 뜻합니다

문제는 이름입니다. NAS 없는 구성인데 응답에 nas 가 있습니다. 클라이언트는
이 두 값을 게이트웨이 식별에 실제로 사용하므로, 지우면 앱의 연결 판정이
깨집니다. 반대로 이름을 바꾸면 앱을 다시 빌드해야 합니다.

  선택지 A   이름 그대로 두고 명세에 "역사적 명칭"으로 기록
  선택지 B   이름을 바꾸고 앱 재빌드 (배포물 교체 발생)
  선택지 C   두 값을 유지하고 별칭 필드를 추가 (전환 기간)

저는 A 를 권합니다. 사용자에게 보이지 않는 내부 필드이고, 재빌드 없이
운영에 들어갈 수 있습니다. 다만 명세에 이름의 유래를 남겨두지 않으면
다음 사람이 "왜 NAS 없는 서버가 nas:true 를 답하나"에서 멈춥니다.
판단 부탁드립니다.

[참고] 앱 진단 문구

설정 화면에 "그 주소는 나스 로그인 화면입니다"라는 안내가 있습니다.
사용자에게 보이는 문구라 결함 2 보다 눈에 띕니다. 다만 이것도 재빌드
사유입니다. 이번에는 손대지 않았습니다.

[결함 3] 가져오기에 경고가 없습니다 — 심각도 높, 고칠 예정

지난 보고 4-3 에서 "가져오기는 덮어쓰기"라고 적고, 안내 문구 한 줄을
요청드렸습니다. 그런데 확인해 보니 문제가 허브 문서가 아니라 앱 안에
있습니다. 가져오기 경로 두 개 모두, 경고 없이 곧바로 실행됩니다. 실수로
누르면 확인 절차 없이 기존 일정이 사라집니다.

  경로 1   붙여넣기 복원 — 다이얼로그에서 복원을 누르면 즉시 덮어씀
  경로 2   파일 선택 복원 — 파일을 고르면 즉시 덮어씀
  공통     "덮어씁니다" 안내도, 되돌리기 수단도 없음

허브 문서에 안내를 넣는 것만으로는 부족합니다. 사용자는 문서를 읽지 않고
버튼을 누릅니다. 그래서 두 가지를 함께 하겠습니다.

  앱     가져오기 실행 전에 확인 단계를 넣고, 아래 문안을 화면에 표시
  허브   scheduler 안내에 같은 문안을 게시

문안은 두 문장으로 확정했습니다. 앱과 허브가 같은 말을 해야 사용자가
헷갈리지 않습니다.

  가져오기 전에 내보내기로 현재 일정을 백업하세요.
  가져오기는 기존 일정과 합치지 않고, 현재 일정을 모두 덮어씁니다.

이 수정은 앱 문구·화면 변경이라 재빌드가 필요합니다. 결함 2(내부 필드명)는
재빌드 없이 가는 쪽을 권했지만, 이 건은 예외입니다. 사용자가 실제로 일정을
잃는 경로이고, 재빌드 비용보다 피해가 큽니다. 다만 배포물이 바뀌므로 새
패키지와 새 지문을 별도로 제출하겠습니다.
