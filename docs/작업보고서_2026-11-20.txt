4. 발견하여 조치한 문제
================================================================================

이번 작업에서 가장 값어치 있는 부분입니다. 만들면서 "만든 것이 실제로
안전한가"를 확인하는 과정에서 문제 3건을 찾았습니다.


[4-1] 제출 패키지에 유출된 동기화 키가 실려 나갈 뻔함  (심각)

  발견 경위
    ZIP 을 만든 뒤 내용을 다시 열어 검사한 결과, 사고 보고서
    INCIDENT-2026-11-20.md 안에 2026-11-20 에 공개 배포본으로 유출된
    동기화 키가 "증거" 명목으로 원문 인용되어 있었고, 그 문서가 제출
    패키지에 그대로 실려 있었습니다.

  원인
    기존 검사는 파일 이름과 웹 번들만 보았습니다. 소스 문서의 내용은
    검사 대상이 아니었습니다.
    증거를 남기려고 값을 원문 인용하는 관행이, 회수 대상 값을 다시
    유통시키는 통로가 되어 있었습니다.

  조치
    1) 검사기 확장 — ZIP 에 들어갈 소스 파일의 내용을 직접 훑는 검사 추가.
       값을 직접 보관하지 않고 해시로 대조하여, 검사기 자신이 위반자가
       되지 않도록 하였습니다.
    2) 유출 키 원문을 소스 트리에서 전량 삭제 (grep 0건 달성)
    3) NAS 호스트명도 삭제 — 자격증명은 아니지만 사고에 이용된 정보이므로
       제3자 패키지에 실을 이유가 없습니다.
    4) 사고 문서에 "값 자체는 증거가 아니다" 라는 취지를 기록

  검증
    역방향 시험까지 수행했습니다.
      정상 소스                → 통과
      유출값을 심은 파일       → 차단 확인
      개인키 헤더를 심은 파일  → 차단 확인
    통과만 확인하면 검사기가 죽어 있어도 알 수 없기 때문에, 반대 방향으로도
    시험했습니다.

  결과
    최종 ZIP 내 유출값 0건, 호스트명 0건


[4-2] 검사기가 자기 자신을 위반자로 신고  (중간)

  증상
    패키징이 "submit_gabia_direct.py 가 개인키를 포함한다" 로 차단됨.

  원인
    검사 대상 스크립트 안에 개인키 헤더 문자열을 통짜로 적어둔 것이
    원인이었습니다. 그 스크립트도 ZIP 에 들어가므로 자기 오탐이 발생.

  조치
    문자열을 조각으로 조립하도록 변경. 탐지 성능은 동일하고 자기 오탐만
    제거. (§4-1 의 해시 대조와 같은 이유)


[4-3] 문서가 사실보다 앞서 나감  (낮음, 그러나 신뢰 문제)

  증상
    ZIP 안의 실행 안내서가 "가상 일정으로 반복·시간대를 검사한다" 고
    기술하고 있었으나, 실제로 그런 테스트가 없었습니다.

  조치
    안내서를 고쳐 쓰는 대신, 테스트를 실제로 작성했습니다(§2 요청2).
    문서를 사실에 맞추는 방법은 두 가지인데, 기능을 빼는 쪽보다
    검사를 만드는 쪽이 사용자에게 이득이므로 후자를 택했습니다.

9. 판단이 필요한 지점
================================================================================

솔직하게 남깁니다.

[9-1] 지금 ZIP 을 보낼 것인가

  현재 ZIP 은 검사는 모두 통과했지만 web/ 이 08:53 빌드본입니다.
  즉 "업데이트 알림 기능이 빠진 버전"입니다.

  선택지
    A) 지금 보낸다 — 검사는 통과했으므로 기술적 결함은 없습니다.
       단 업데이트 알림이 없는 버전으로 제출됩니다.
    B) 팝업 연결 후 새로 빌드해 보낸다 — 하루 정도 더 걸립니다.

  제 의견
    B 를 권합니다. 수신기 규격도 아직 확정 전이므로 급할 이유가 없고,
    한 번 제출한 릴리스는 덮어쓰지 않는 설계이기 때문입니다
    (같은 릴리스 ID 는 409 로 거절). 나중에 고치려면 새 릴리스로 다시
    내야 합니다.

[9-2] 업로드 판정 기준을 낮출 것인가

  권하지 않습니다. "서버가 계산한 해시가 일치할 때만 접수 완료"는
  실제로 파일이 온전히 도착했는지를 확인하는 유일한 수단입니다.
  이 기준을 낮추면 전송 중 잘린 파일도 "접수 완료"로 보고하게 됩니다.

10. 총평
================================================================================

요청하신 기능은 구현과 검증을 마쳤고, 자격증명만 없어 전송 단계에서
멈춰 있습니다.

다만 이번 작업의 실질적 성과는 기능 추가가 아니라, 제출 패키지에 유출된
키가 실려 나갈 뻔한 것을 잡아낸 것입니다. "제외 규칙을 코드로 썼다"와
"그 규칙이 실제로 동작했다"가 다르다는 점, 그리고 확인하지 않은 것을
확인했다고 말하지 않는다는 원칙이 실제로 작동한 사례입니다.

남은 것은 두 가지입니다. 업데이트 팝업 연결(제 몫), 그리고 수신기
자격증명과 보안 후속 조치(승준님 몫).
