1. 회신의 지적을 어떻게 받아들였는지
================================================================================

회신의 핵심 지적은 "테스트 통과를 이전 완료로 확대 해석하지 말라"였습니다.
타당한 지적이라 판단해 이번 보고의 형식을 바꿨습니다. 측정한 것과 하지 않은
것을 한 표에 섞지 않고 5장에서 완전히 분리했습니다.

또 하나 받아들인 부분은 "GitHub Pages 운영 보고는 접수했으나 직접 검증하지
않았다"는 단서입니다. 저도 같은 태도로 임하겠습니다. 이 보고의 수치는 전부
제가 이 환경에서 직접 실행해 얻은 값이며, 그 범위를 벗어난 판단은 하지
않습니다.

  이 보고가 보증하는 것

    - 기재된 커밋의 소스와 기재된 패키지의 빌드 산출물이 서로 일치한다
    - 그 패키지를 정적 파일로 서빙하면 앱이 뜨고 일정이 유지된다
    - 내보내기·가져오기가 실제로 왕복하며, 가져오기는 덮어쓰기다

  이 보고가 보증하지 않는 것

    - 가비아 서버에서 그 패키지가 정상 동작한다 (아직 올리지 않았습니다)
    - 가비아 Nginx·HTTPS·WASM MIME 이 올바르다 (실환경 미확인)
    - 8097 게이트웨이가 가비아에서 뜬다 (이번 시험 대상이 아닙니다)
    - 허브의 scheduler 카드가 어떤 상태를 표시해야 하는지 (허브 측 판단)

2. 이번에 연결한 것 — 업데이트 감지
================================================================================

[2-1] 무엇을 만들었나

앱을 열면 서버의 version.json 을 읽어, 지금 실행 중인 빌드와 다르면 팝업을
띄웁니다. 「나중에」는 3일 뒤로 미루고, 「지금 업데이트」는 서비스 워커와
캐시를 지운 뒤 새 주소로 다시 엽니다.

  확인 주기 : 12시간
  미루기    : 3일
  실패 시   : 조용히 무시 (앱 시작을 막지 않습니다)

[2-2] 왜 이게 필요했나 — PWA 구버전 캐시 문제

회신에서 지적하신 "PWA 구버전 캐시"가 정확히 이 문제입니다. Flutter 웹은
flutter_service_worker.js 를 남기고, 그 안의 RESOURCES 목록에 version.json 이
들어 있습니다. 문제는 이 목록에 있는 파일을 캐시 우선으로 처리한다는 점입니다.

결과적으로 서버에 새 버전이 올라가도 브라우저는 자기가 가진 옛 version.json 을
읽고 "이미 최신"이라고 답합니다. 이 상태로는 업데이트 팝업이 영원히 뜨지
않습니다. 실제로 첫 구현이 이 함정에 빠졌고, 팝업이 안 뜨는 것을 기능 실패로
오판할 뻔했습니다.

[2-3] 어떻게 해결했나

version.json 요청에 매번 다른 쿼리 문자열을 붙였습니다. RESOURCES 목록에 없는
주소가 되므로 서비스 워커가 개입하지 않고 네트워크로 나갑니다. 헤더로도
no-store / no-cache / Pragma 를 함께 보냅니다.

중요한 점은 헤더만으로는 부족했다는 것입니다. 원인은 캐시 정책이 아니라
서비스 워커의 분기 구조였습니다. 이 사실을 명세에 남겨두시면 나중에 같은
문제를 반복하지 않습니다.

[2-4] 브라우저 실측 결과

시험 방법은 이렇습니다. 헤드리스 브라우저에서 서버가 광고하는 빌드 값만
올리고 실제 번들은 그대로 두어, "번들은 구버전, 서버는 신버전" 조건을
재현했습니다.

  서버가 광고한 값 : 2026.11.20.1500
  실행 중이던 번들 : 2026.11.20.1400
  팝업 표시        : 떴습니다

처음에는 번들과 version.json 을 함께 바꿔 시험했습니다. 그때는 팝업이 안
떴는데 그게 정상이었습니다. 새로고침 과정에서 서비스 워커가 새 번들로 자동
갱신되어 두 값이 이미 같아졌기 때문입니다. 시험 설계가 틀렸던 것이지 기능이
틀린 것이 아니었습니다. 두 값을 따로 제어하도록 시험대를 고친 뒤에야 올바른
조건을 만들 수 있었습니다.

[4-1] 이번 시험의 경계

  연결한 것     : 정적 파일 서빙만
  연결 안 한 것 : 동기화 게이트웨이(8097), 실제 NAS, 허브 서비스, 운영 데이터

회신에서 "정적 파일만 교체할 때 Node 재시작은 필요하지 않을 수 있다"고 하신
부분과 같은 방향입니다. 이번에는 Node 쪽을 아예 띄우지 않고, 정적 번들만으로
앱이 완전히 동작하는지 먼저 확인했습니다.

[4-2] 가상 일정으로 확인한 것

실제 일정·계정·OAuth 토큰은 쓰지 않았습니다. 전부 메모리 안의 가상 데이터
입니다.

  항목                      결과
  -----------------------   ----------------------------------------
  로그인 화면 표시          정상 (흰 화면 아님)
  새로고침 후 일정 유지     13건 그대로
  내보내기                  성공 — 11,006자 / 13건
  가져오기                  성공 — 시험일정 A·B·C 복원
  동기화 설정               건드리지 않음 (기본값 유지)

"새로고침 후 유지"는 특히 중요합니다. URL 라우팅을 쓰지 않는 구성이라 하위
경로에서 새로고침해도 404 가 나지 않아야 하고, 저장소는 브라우저 IndexedDB
에 남아 있어야 합니다. 둘 다 확인했습니다.

[4-3] 가져오기는 덮어쓰기입니다 — 증거

이건 사용자 안내에 반드시 들어가야 할 성질이라 실측으로 확정했습니다.

  1) 고유 표식이 되는 일정을 하나 만들었습니다 (가져오면 사라져야 하는 항목)
  2) 가져오기 직전 — 일정 12건, 표식 있음
  3) 가져오기 실행
  4) 가져온 직후 — 일정 11건, 표식 없음, 백업의 A·B·C 는 복원됨

코드도 같은 동작입니다. 가져오기 함수가 일정·분류·기록·음성 저장소를 먼저
비우고 백업 내용으로 채웁니다. 병합이 아닙니다.

그래서 가져오기 전에 반드시 현재 상태를 먼저 내보내 두어야 합니다. 앱의 설정
화면에 내보내기와 가져오기가 나란히 있으니, 안내 문구는 "가져오기 전에
내보내기로 현재 상태를 저장하세요" 한 줄이면 충분합니다. 이 문구를 넣는 것은
UI 변경이라 지시 없이 손대지 않았습니다.

[4-4] 저장소 이전에 대한 답

회신에서 "NAS 의 일정 JSON 을 로컬로 이전한다면 원본 기준 저장소, 쓰기 중단
시점, 최종 동기화, 롤백 방법을 정해야 한다"고 하셨습니다. 동의합니다. 이번
작업은 그 이전을 하지 않았으므로 이 항목들은 여전히 미정입니다.

다만 이전에 쓸 수 있는 도구는 이번에 검증했습니다. 내보내기로 현재 상태를
파일 하나로 떠 둘 수 있고, 되돌릴 때는 그 파일을 가져오면 됩니다. 두 저장소에
동시에 쓰는 상태는 이번에도 만들지 않았습니다.

  상세 기록 : 패키지 안 test_results.txt

건너뛴 6건은 모두 같은 이유입니다. live 게이트웨이 주소를 환경변수로 주지
않으면 스스로 skip 하도록 만들어 두었습니다. 이 검사들은 가비아 게이트웨이가
실제로 뜬 뒤에 다시 돌려야 의미가 있습니다.

6. 회신 항목별 답
================================================================================

[6-1] pending 유지 — 동의하고 요청합니다

이번 보고로 live 전환을 요청하지 않습니다. 가비아 실환경 검증 전에는 pending
이 맞습니다. live 를 "운영자가 검증 후 연결을 게시했다"는 의미로 관리하신다는
정의에도 동의합니다.

[6-2] 내부 포트 8097 — 유지 동의

코드의 기본값을 확인했습니다. 포트는 환경변수 PORT, 기본 8097 입니다. 바인딩은
기본 127.0.0.1 이고, 0.0.0.0 은 명시적으로 지정해야만 됩니다.

회신에서 "PORT=8097 node ... 만으로는 loopback 이 보장되지 않는다"고 하셨는데,
이 소스는 기본값이 loopback 이라 지정하지 않으면 외부에 열리지 않습니다.
다만 지적의 취지에는 동의합니다. 실제 호스트에서 확인해야 합니다.

  ss -ltnp 로 127.0.0.1:8097 인지 확인 (0.0.0.0 이면 즉시 중지)
  같은 포트를 쓰는 다른 프로세스가 없는지 확인
  방화벽에서 8097 이 외부로 열려 있지 않은지 확인

[6-3] /health 유지 — 동의, 의미는 이렇게 정의되어 있습니다

회신에서 세 가지 중 무엇인지 물으셨습니다. 소스 기준 답은 첫 번째에 가깝고,
저장 모드에 따라 대상이 달라집니다.

  묻는 것         : 지금 이 순간 백엔드가 응답하는가 (가벼운 생존 확인)
  저장 모드 local : 데이터 디렉터리에 쓸 수 있는가
  저장 모드 dsm   : NAS 세션이 살아 있는가
  응답 내용       : 상태 한 비트와 서비스 식별자 — 그게 전부입니다
  넣지 않은 것    : 저장 경로, 내부 설정, 시각

저장 경로와 시각을 뺀 이유는 정찰에 쓸모가 있고 클라이언트는 읽지 않는
값이기 때문입니다. 회신의 우려, 즉 "STORAGE=local 로 바꿔도 무조건 NAS
기준으로 동작하면 안 된다"는 지적은 이미 반영되어 있습니다. 저장 모드별로
서로의 저장소를 건드리지 않습니다. local 모드에서 NAS 가 죽어 있어도 자기
자신을 down 이라고 답하지 않습니다.

Nginx 에서 /health 를 정적 경로와 분리해 게이트웨이로 넘겨야 한다는 점도
동의합니다. 이번 시험은 정적 전용이라 해당 없음입니다.

[6-4] /readyz — 이미 구현되어 있습니다 (회신 대비 진전 사항)

회신에서는 "추가를 권장"하신 상태였습니다. 확인 결과 이미 구현되어 있고,
요청하신 조건을 만족합니다.

  경로        GET /readyz
  정상        HTTP 200, 준비 안 됨 HTTP 503
  응답        준비됨은 최소 응답, 미준비는 세 단어 사유
  사유 값     config / auth / storage 세 가지뿐
  금지 사항   경로·호스트·자격증명 노출, 사용자 데이터 열거, 데이터 변경
  캐시        no-store

쓰기 가능 여부를 디렉터리 권한만으로 판단하지 않는다는 점도 요청하신 수준에
맞습니다. 점으로 시작하는 임시 파일 하나를 실제로 쓰고 읽고 지워 확인합니다.
이 파일명은 일정 파일 이름 규칙에 맞지 않아, 사용자 데이터로 오인되거나
목록에 섞이지 않습니다.

또한 /readyz 결과를 5초간 재사용합니다. 매 초 도는 검사가 매번 NAS 로그인을
하지 않게 하려는 것이고, 동시에 오래된 "준비됨"이 트래픽을 붙잡아 두지
않도록 짧게 잡았습니다.

다만 이 구현은 게이트웨이를 띄운 상태에서의 이야기입니다. 이번 시험은 정적
전용이라 /readyz 를 실제로 호출해 확인하지는 않았습니다. 이 점은 분명히
해 둡니다.

[6-5] 동일 출처 /api/ — 동의, 접두사 규칙 확정 요청

회신에서 지적하신 대로 접두사 유지 또는 제거 중 하나를 정해야 합니다. 현재
게이트웨이의 실제 경로는 /api/state, /api/push, /api/reset, /api/drop 입니다.
따라서 접두사를 유지하는 쪽이 맞습니다.

  proxy_pass http://127.0.0.1:8097;     ← 접두사 유지 (이쪽을 제안)

끝에 슬래시를 붙이면 접두사가 잘려 404 가 됩니다. 이 값은 허브 명세에서
TO_BE_CONFIRMED 로 두신 항목이라, 위 값으로 확정해 주시면 맞춰 두겠습니다.

/health 와 /readyz 는 /api/ 밖의 루트 경로입니다. 따라서 /api/ 설정만으로는
부족하고 두 경로를 따로 넘겨야 합니다. 이 지적도 맞습니다.

동일 출처가 인증을 대신하지 않는다는 점에는 전적으로 동의합니다. 서버 측
사용자 인증, 사용자별 권한, CSRF 대응은 아직 없는 상태이며 이번 시험 범위도
아닙니다. 동기화를 켜지 않으면 해당 통로 자체가 열리지 않습니다.

[6-6] WASM MIME — 목표 확인, 실환경 미검증

Nginx 는 .htaccess 를 읽지 않으므로 논점이 "허용 여부"가 아니라 "우리가 설치한
Nginx 가 올바로 서빙하는가"라는 지적에 동의합니다. 목표 값은
application/wasm 입니다. 이번 시험 절차서에 이 항목을 확인 목록으로 넣어
두었습니다. 실환경 확인은 아직입니다.

[6-7] 두 배포물 분리 — 동의

사용자 화면에는 scheduler 한 항목, 운영 명세에는 정적 번들과 게이트웨이 두
구성요소로 나누는 안에 동의합니다. 시험 절차서도 이 구조를 전제로 작성했습니다.
다만 이번 시험은 정적 번들만 대상입니다.

  기존 경로 : 건드리지 않음 (읽기조차 하지 않음)

[8-3] 두 가지 방법 중 하나

방법 A — Nginx 설정을 새 파일로만 추가합니다. 기존 80/443 을 쓰지 않고 별도
포트로만 열며, 설정은 새 파일 하나만 추가합니다. 기존 설정 파일은 수정하지
않습니다.

방법 B — Nginx 를 아예 건드리지 않습니다. 파이썬 기본 서버를 loopback 에만
바인딩해 띄우고 확인은 SSH 터널로 합니다. 방화벽 변경이 전혀 필요 없습니다.
기존 서비스에 영향을 줄 가능성이 가장 낮아 이쪽을 권합니다.

[8-4] 확인 목록 여덟 가지

  응답 200 과 no-store 헤더
  version.json 의 build 값이 기대값과 일치
  WASM 응답 Content-Type 이 application/wasm
  로그인 화면이 뜬다 (흰 화면 아님)
  화면 하단 빌드 표기 일치
  새로고침해도 404 없음
  main.dart.js 200 응답
  동기화 설정은 손대지 않음

[8-5] 중지와 복구

시험이 끝나면 시험 경로를 지우고 기존 서비스가 그대로인지 확인하는 절차까지
넣었습니다. 마지막 확인은 기존 설정 검사 통과, 기존 서비스 active, 기존 주소
응답 정상 세 가지입니다.

복구 확인에는 시험 흔적이 0건인지 세는 항목도 넣었습니다. 흔적이 남아 있으면
복구가 끝난 것이 아니기 때문입니다.

9. 관리자가 바로 하실 다음 작업 한 가지

방법 B 로 시험 기동 하나만 해 주십시오.

  패키지의 web/ 디렉터리를 별도 시험 경로에 풀고, loopback 에만 바인딩한

흰 화면이면 그 자리에서 멈추고 저에게 알려 주십시오. 원인은 사실상 MIME 또는
base-href 두 가지로 좁혀집니다.

이 확인이 끝나면 다음 단계(허브 링크 연결 여부)를 별도로 협의하겠습니다.
이번 보고로 허브 상태를 바꿔 달라는 요청은 없습니다.

10. 요청드리는 판단 세 가지

하나. /api/ 접두사는 유지(끝 슬래시 없음)로 확정해 주십시오. 함께 /health 와

live 전환은 가비아 실환경 확인 후 별도로 요청하겠습니다.
